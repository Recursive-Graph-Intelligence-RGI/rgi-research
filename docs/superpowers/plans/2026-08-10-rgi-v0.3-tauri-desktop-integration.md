# RGI v0.3 Tauri + RGI Desktop Integration Plan

**Date:** 2026-08-10  
**Status:** Draft plan  
**Scope:** Focus v0.3 product work on the Tauri desktop path with RGI as the cognitive backend.  
**Constraints:** Do not modify `/home/jeff/projects/rlmlocal-site`. RGI changes only.

## Goal

Deliver a working desktop integration where the Tauri shell from `rlmlocal-site` can spawn the RGI Python engine, send it a repository path and objective, and receive a streamed analysis result.

This replaces the browser-only/local-ML limitation of the PWA with a local recursive-graph intelligence engine that has full filesystem access and FortSignal governance.

## Why this path

- The web/PWA path cannot run Python/RGI in the browser.
- Tauri already exists in `rlmlocal-site` and provides the native shell needed to spawn RGI.
- RGI is already a working Python engine with perception, recursive execution, and grounded tools.
- FortSignal governance naturally maps to the Rust shell (hard limits) + Python engine (semantic policy).

## Architecture

```
┌──────────────────────────────────────────────┐
│  rlmlocal desktop (Tauri)                    │
│  ┌──────────────┐   invoke/commands   ┌────┐ │
│  │  TS/Vite UI  │ ←────────────────→  │Rust│ │
│  └──────────────┘                     └─┬──┘ │
└─────────────────────────────────────────┼────┘
                                          │ spawns / monitors
                                          ▼
┌──────────────────────────────────────────────┐
│  RGI Python engine (local HTTP service)      │
│  - POST /analyze                             │
│  - GET  /jobs/{id}/status                    │
│  - GET  /jobs/{id}/result                    │
│  - POST /shutdown                            │
└──────────────────────────────────────────────┘
```

RGI exposes an HTTP API. The Tauri Rust shell starts the Python process, discovers its port, and forwards calls from the webview.

## Milestones

### Milestone 1 — HTTP service mode for RGI

**Files:**
- Create: `rgi/server.py`
- Modify: `rgi/cli.py` to support `python -m rgi server --port 8787`
- Test: `tests/test_server.py`

**Interfaces:**
- `POST /analyze` → `{path, objective, model?, max_llm_calls?}` → `{job_id}`
- `GET /jobs/{id}/status` → `{status, progress, logs: [...]}`
- `GET /jobs/{id}/result` → final report JSON
- `POST /shutdown` → graceful exit

**Implementation notes:**
- Use `asyncio` + `aiohttp` or Python's `http.server` with async handlers.
- Run `run_analysis` in a background task.
- Stream progress via an in-memory job store.
- Keep the existing CLI behavior unchanged.

## IPC decision

**HTTP/REST for v0.3.** It is simple, debuggable with `curl`, and easy to bridge from Tauri. gRPC or Unix-domain sockets can be evaluated later if HTTP latency becomes a bottleneck.

## Deployment targets

| Target | Shell | Transport |
|---|---|---|
| Local desktop (primary) | Tauri from `rlmlocal-site` | HTTP to local RGI |
| CI / batch | None | Direct `python -m rgi analyze` |
| Cloud | Container | HTTP service |

## Open questions

1. Should the RGI server bundle its own Python runtime, or require system Python?
2. How does the Tauri shell discover the correct RGI installation path?
3. Should the server stream SSE events, or should the UI poll `/jobs/{id}/status`?
4. Where does the policy file live: user config, project config, or both?

## Success criteria

- `python -m rgi server` starts and responds to HTTP requests.
- The Tauri sidecar example can spawn RGI, run an analysis, and display results.
- Existing CLI and test suite remain green.
- No modifications to `rlmlocal-site`.
