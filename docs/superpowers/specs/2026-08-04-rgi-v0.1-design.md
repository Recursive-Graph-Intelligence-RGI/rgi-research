# RGI v0.1 — Recursive Graph Intelligence Prototype — Design

Date: 2026-08-04
Status: Approved for planning

## 1. Mission

Prove that recursive graph decomposition + structured graph memory + topological
self-correction outperforms a monolithic agent loop on complex multi-step tasks.
The LLM is a **reasoning primitive inside nodes** — it never orchestrates.
Intelligence claims rest on graph topology, feedback loops, and recursive spawning.

The brain model (activation-as-attention, harness-as-basal-ganglia,
verification-as-ACC, learning-as-plasticity) is the **architectural language and
North Star**, not the v0.1 implementation target. v0.1 builds the formal,
evaluable version; v0.2/v0.3 evolve the dynamics (spreading activation,
inhibition-default harness, Hebbian edge updates) behind stable interfaces.

## 2. Demo Scenario

```
python -m rgi analyze ./sample_project --objective "Analyze authentication security" --output report.json
```

`sample_project/` is a 4-file Python web app with intentional auth vulnerabilities:
- `auth.py` — JWT handling, missing expiration check, weak secret
- `session.py` — session management without timeout
- `login.py` — password check without hashing
- `config.py` — hardcoded API key

Output: structured JSON report — findings, confidence scores, graph topology
used, correction history log.

## 3. Architecture

### 3.1 Data model (fixed)

Pydantic v2, UUID-string IDs. Models exactly as specified in the master prompt:
`NodeType`, `LoopType`, `NodeState`, `CognitiveNode`, `CognitiveEdge`,
`GraphState`, `GraphPolicy`, `CognitiveGraph` (G = (V, E, S, P)).

### 3.2 Engine — `core/engine.py`

`execute_graph(graph, harness) -> graph`: five-phase loop per iteration —
1. **Activation**: score nodes, threshold at 0.5, sort descending.
2. **Node execution**: governance check → dispatch by node type
   (REASONING → LLM JSON call; TOOL → registry; VERIFICATION → challenge
   connected nodes, may trigger correction; GOVERNANCE → policy eval).
3. **Graph evolution**: spawn proposals → harness approval → sibling subgraphs
   executed concurrently via `asyncio.gather` → merge results.
4. **Verification & consolidation**: spawn verification subgraph if policy
   requires and none exists; aggregate confidence vs threshold → completed/failed.
5. **Learning update**: record pathway.

Every decision (spawn, inhibit/reject, correct, terminate) is recorded in graph
state history and the audit log.

### 3.3 Harness — `core/harness.py`

Permission-scheduler stance for v0.1 (inhibition-default is v0.3). Hard caps:
max depth 3, max 50 total nodes across all graphs, max 20 LLM calls, max 5 min
wall clock. Global `asyncio.Lock` on `request_subgraph_spawn`. Every rejection
logged with reason to the audit trail.

`governance_check(graph, node)` delegates to the **GovernanceGate** interface
(§3.7). Default adapter is local; FortSignal adapter is Phase 2.
Contains `# TODO: Integrate FortSignal for identity, risk, and policy context`.

### 3.4 Activation engine — `memory/activation.py`

Brain-shaped interface: `propagate(graph, objective) -> {node_id: score}`.
v0.1 internals: keyword-seed matching on node content → one-hop propagation
along edges with 0.8 decay × edge weight → +0.1 history bonus for nodes in past
successful corrections → cap 1.0. No embeddings in v0.1; v0.2 swaps internals
only (interface unchanged).

### 3.5 Perception — `perception/code_parser.py`

`ast`-based ingestion of the target codebase → KNOWLEDGE graph: classes,
functions, imports as entity nodes; typed edges (calls / imports / depends_on);
confidence 1.0 for parsed syntax, 0.7 for inferred relationships. No external
parser dependency.

### 3.6 LLM client — `reasoning/llm_client.py`

Interface: `async reason(task: str, context: str) -> dict` returning
`{finding, confidence, reasoning, recommended_action, suggested_subgraphs}`.

Two implementations behind the interface:
- **Real client**: OpenAI-compatible chat-completions over `httpx`, JSON mode.
  Configured by env: `RGI_LLM_BASE_URL`, `RGI_LLM_API_KEY`, `RGI_LLM_MODEL`.
  Preset `--provider kimi` fills Moonshot/Kimi defaults (OpenAI-compatible
  endpoint); exact model name confirmed against the user's Moonshot console at
  first live run. Anthropic would be a second client later — not built now.
- **Mock client**: deterministic fixture-driven responses; used by all tests
  and by keyless runs; `--mock` CLI flag forces it.

`LLMClient` increments `harness.total_llm_calls`; harness rejects calls past 20.

### 3.7 Governance gate — `core/governance.py` (new vs master prompt)

```python
class GovernanceGate(Protocol):
    async def check(self, action: str, params: dict) -> GateDecision  # allow/deny + reason
```

- `LocalGate` (default): file-scope allowlist (tool paths must stay under the
  analysis target), LLM budget, node policies. Deterministic, offline.
- `FortSignalGate` (Phase 2, interface stub only in v0.1): maps spawn / tool /
  LLM-call actions to FortSignal challenge/verify; receipts (`signalId`,
  `policyId`, deny reason codes) flow into the audit log. Requires
  `FORTSIGNAL_API_KEY` / agent credentials; never required for tests or mock
  runs.

Rationale: [fortsignal.com](https://fortsignal.com) is a deterministic
enforcement gate (cryptographic intent binding, delegation caps, signed
receipts) — aligned with "safety engineered, not prompted" — but v0.1 must run
reproducibly without a SaaS dependency.

### 3.8 Audit trail — `data/audit.jsonl` (first-class deliverable)

Every spawn approval/rejection, governance decision, correction trigger, and
termination appended as a JSON line: `{timestamp, event, graph_id, details}`.
Governance you can't replay isn't governance.

### 3.9 Learning engine — `loops/learning.py`

`record_pathway(graph)`: objective → topology (node types + edges) → outcome,
persisted to `data/pathways.json`. v0.1 records; v0.3 uses it for edge-weight
updates (Hebbian). Interface leaves room; implementation doesn't.

### 3.10 Context builder — `core/context_builder.py`

Targeted LLM context: node content + up to 5 highest-activated neighbors
(activation > 0.3) + graph memory snapshot + policy constraints + prior attempt
history (only when correcting). Hard cap ~4000 tokens. The LLM never sees the
whole system.

### 3.11 Tool registry — `tools/registry.py`

Tools: `parse_python_file`, `grep_security_patterns`, `check_jwt_usage`,
`find_hardcoded_secrets`. Each returns `{findings, confidence, ...}`.
Tool execution is governance-checked (path scope).

## 4. Demo Flow (end-to-end)

0. Perception ingests `sample_project/` → KNOWLEDGE graph (JWTManager,
   SessionStore, LoginHandler, Config + typed edges).
1. Root PLANNING graph runs; planning node returns suggested subgraphs.
2. Harness approves 2 EXECUTION subgraphs at depth 1 (JWT analysis, session
   analysis); they run concurrently.
3. JWT graph returns confidence 0.6 (< 0.7 threshold) → VERIFICATION subgraph
   at depth 2 challenges → confirms the finding is real and under-confident →
   `finding_valid: false` → **correction**: new EXECUTION graph with stricter
   parameters; original node goes CORRECTING → COMPLETED after merge
   (confidence 0.88).
4. Planning graph sees JWT complexity → spawns "JWT Deep Dive" subgraph.
5. All subgraphs complete → root verification → aggregate confidence 0.87 →
   status completed.
6. Learning engine records pathway; audit log holds every decision.
7. CLI prints report JSON (objective, status, aggregate_confidence,
   corrections_made, graphs_spawned, max_depth_reached, findings,
   topology_used, execution_log).

## 5. Persistence & Visualization

- `data/` — graph states, pathways, memory snapshots, `audit.jsonl` (JSON).
- Mermaid export of final topology for the report/README debugging.

## 6. Testing (pytest + pytest-asyncio, all on mock LLM)

1. Recursive spawning stops at max_depth (chain of 5 spawn attempts with
   max_depth=2 → 2 created, 3 rejected with logged reasons).
2. Harness rejects spawn when total node limit reached.
3. Self-correction changes topology (verification triggers a NEW execution
   graph; original node passes through CORRECTING).
4. Aggregate confidence increases after correction.
5. End-to-end mock run of the demo scenario completes < 5 min and < 20 LLM
   (mock) calls, producing a valid report.json.
6. Governance: tool call with path outside target dir is denied and logged.

## 7. Success Criteria (pass/fail)

- Single CLI input autonomously spawns ≥ 3 subgraphs.
- ≥ 1 self-correction event (verification → new execution graph).
- Graph memory persists ≥ 5 entities with typed relationships.
- No graph at depth > 3 (harness-enforced, test-proven).
- Output includes confidence scores, correction history, spawned topology.
- Completes < 20 LLM calls and < 5 minutes on the 4-file codebase.

## 8. Non-goals (explicitly out of v0.1)

- Inhibition-default harness, continuous cross-loop coupling, Hebbian edge
  updates, embeddings/vector search (v0.2–v0.3).
- Live FortSignal integration (interface stub only).
- Anthropic-specific client, framework/plugin system, protocol spec (Phase 2+).
- Learned activation/spawn policies (GNN-style message passing or policy
  networks) — a v0.3+ research direction, gated on accumulated pathway data
  (~thousands of logged runs). v0.1's activation engine and spawn approval
  interfaces are the seams where such learned components would later plug in.

## 9. File Layout

Per the master prompt's structure, plus:
- `rgi/core/governance.py` — GovernanceGate protocol + LocalGate (+ FortSignal stub)
- `rgi/core/audit.py` — audit.jsonl writer
- `rgi/reasoning/llm_client.py` — real (OpenAI-compatible) + mock clients

```
rgi-prototype/
├── rgi/ (core/, loops/, memory/, perception/, reasoning/, tools/, cli.py)
├── sample_project/ (auth.py, session.py, login.py, config.py)
├── tests/ (test_harness_limits.py, test_recursive_spawn.py,
│          test_self_correction.py, test_e2e_mock.py, test_governance.py)
├── data/
├── requirements.txt
└── README.md (Mermaid architecture diagram + run instructions)
```
